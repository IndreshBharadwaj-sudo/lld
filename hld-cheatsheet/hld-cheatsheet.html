📖 Chapter 1: Scale From Zero To Millions of Users

📋 SUMMARY
Covers the evolutionary journey of scaling a system from a single server to distributed architecture. Key trade-off: Simplicity vs. Scalability - each step adds complexity but enables handling more traffic.

Evolution: Single Server → Separate DB → Load Balancer → DB Replication → Cache → CDN → Stateless → Data Centers → Message Queues → Sharding

🔹 Vertical vs Horizontal Scaling

Vertical (Scale Up)Horizontal (Scale Out)
Add more CPU, RAM to one serverAdd more servers
Simple but has hard limitsNo hard limit
Single point of failureRequires load balancer

🔹 Load Balancer

  • Distributes traffic across multiple servers
  • Provides failover capability
  • Has a public IP, while servers have private IP
  • Algorithms: Round Robin, Least Connections, IP Hash
  • Examples: HAProxy, Nginx, F5

🎯 DB Choice – System Design Cheat Sheet

📊 Data Types:
Structured → users, transactions, orders
Semi-structured → JSON profiles, catalogs
Unstructured → logs, images, videos

🔍 Access Pattern:
SQL → joins, aggregations, complex queries
NoSQL → key-based access, simple queries

📈 Scale:
Read-heavy / write-heavy / massive data volume

🔒 Consistency:
SQL → strong consistency (ACID on primary)
Replicas → may be eventually consistent (lag)
NoSQL → eventual consistency by default (can be tuned stronger)

🧱 SQL Databases:
PostgreSQL, MySQL, Oracle, SQL Server
Best for structured data, transactions, joins
Scaling → vertical → read replicas → cache → sharding

🌐 NoSQL Databases:
MongoDB, Cassandra, DynamoDB, Redis, HBase
Best for high scale, flexible schema, low latency
Scaling → built-in sharding + replication

⚖️ SQL vs NoSQL Consistency:
SQL → single primary + coordination → strong consistency
NoSQL → distributed writes + less coordination → eventual consistency

🔥 Why Writes Are Harder to Scale In SQL DBs:
Reads → easy (served from replicas)
Writes → require coordination (transactions, constraints, indexes)
Sharding issues → cross-shard joins, distributed transactions, hot partitions
Key idea → Reads = copy problem, Writes = coordination problem

🚀 Hybrid Approach:
SQL → transactions / source of truth
Redis → caching
NoSQL → logs, analytics, high-scale data

🎯 Summary:
SQL → correctness + relationships
NoSQL → scalability + flexibility
Real systems → hybrid approach

🔹 Database Replication (Master-Slave)

  • Master: Handles all writes
  • Slaves: Handle reads (can have multiple)
  • Trade-off: Replication lag vs. read scalability due to replication lag for read replicas
  • Failover: Promote slave to master if master fails
  • Replication also provides Better performance, Reliability, High availibility

🔹 Cache

  • Temporary storage for frequently accessed data
  • Types: Redis, Memcached
  • Strategies: Cache-aside, Write-through, Write-behind
  • Eviction: LRU (Least Recently Used), LFU

🔹 CDN (Content Delivery Network)

  • Geographically distributed servers for static content like images, videos, CSS, JavaScript files, etc.
  • Reduces latency for end users
  • Push CDN: Upload content proactively
  • Pull CDN: Fetch on first request

🔹 Stateless Architecture

  • No session data stored on web servers
  • Session state moved to shared storage (Redis)
  • Any server can handle any request
  • Enables easy horizontal scaling

🔹 Message Queue

  • Decouples components for async processing
  • Examples: RabbitMQ, Kafka, Amazon SQS
  • Producers → Queue → Consumers
  • Enables independent scaling

🔹 Data Centers

  • To geo route data
  • Also in case of any disaster

🔹 Logging, metrics, automation

📊 Logging, Metrics & Automation:
Needed at scale for reliability, visibility, and productivity

📝 Logging:

📈 Metrics:

📖 Chapter 4: Design A Rate Limiter

📋 SUMMARY
For now, we only need to know that the API gateway is a middleware that supports rate limiting.
Controls the rate of traffic from clients. Prevents DoS attacks, reduces cost, prevents overload. Trade-offs: Accuracy vs. Performance (distributed sync overhead), User Experience vs. Protection.

🔹 Rate Limiting Algorithms

AlgorithmProsCons
Token BucketMemory efficient, allows burstsTuning is challenging
Leaking BucketSmooth output, memory efficientBurst fills queue, starvation
Fixed Window of requests per time unitMemory efficient, simpleBurst at window edges (2x)
Sliding Window LogVery accurateMemory intensive
Sliding Window CounterSmooths burst, efficientApproximate

🔹 Token Bucket (Most Popular)

  • Tokens added at fixed rate to bucket
  • Request consumes a token; rejected if empty
  • Bucket size = burst capacity
  • Used by: Amazon, Stripe

🔹 Leaky Bucket (Smooth Rate Limiting)

  • Requests added to bucket (queue)
  • Processed at constant fixed rate
  • Excess requests dropped if bucket is full
  • Ensures steady output (no bursts)
  • Used by: Network traffic shaping, APIs needing stable rate

🔹 Sliding Window Log (Accurate but Heavy)

  • Store timestamp of each request
  • Remove timestamps outside time window from current time t
  • Allow request if count within limit
  • Highly accurate rate limiting
  • There is no one consuming contunuosly, when a req comes we check how many we processed and based on that we accept or reject
  • Cons: High memory usage (stores all requests), cleanup overhead
  • Used by: Systems needing strict accuracy

🔹 Sliding Window Counter (Optimized Approximation)

  • Divide time into fixed intervals (window_size)
  • Interval: Fixed time range based on system time (e.g., [0–10), [10–20))
  • Bucket calculation: bucket_id = floor(current_time / window_size)
  • Current bucket: count of requests in current interval
  • Previous bucket: count of requests in last interval
  • How requests are tracked:
    • If bucket_id == current → increment current_count
    • If bucket changes → shift current → previous, reset current
    • If gap > 1 bucket → reset both counts
  • Effective count:
    current_count + previous_count × (remaining_time / window_size)
  • Pros: Low memory, fast (O(1))
  • Cons: Approximate (less accurate than sliding log)
  • Used by: High-scale APIs needing efficiency

🔹 HTTP Headers

HeaderDescription
X-Ratelimit-RemainingRemaining requests in window
X-Ratelimit-LimitTotal allowed requests
X-Ratelimit-Retry-AfterSeconds to wait
HTTP 429Too Many Requests

🔹 Distributed Rate Limiting

  • Challenge: Race condition (concurrent read-modify-write), Synchronijation issue across nodes of web server
  • Locks are obvious solution but it will slow down the system.
  • Solution: Lua scripts for race conditions in Redis (atomic operations)
  • Solution: Having centralid reddis for synchronition, so no need to store counts on web servers
  • Storage: Redis cluster for central data store (non-sticky sessions)

🔹 Performance Optimizations

  • Multi-data centre
  • Eventual consistency for Consistency across data centre

🔹 Monitoring

  • Analytics for:
  • The rate limiting algorithm is effective.
  • The rate limiting rules are effective.

📖 Chapter 5: Design Consistent Hashing

📋 SUMMARY
Distributes data/load across servers while minimizing reorganization when servers change. Traditional hash fails when N changes (rehashes everything). Consistent hashing only remaps K/N keys on average. Used by DynamoDB, Cassandra, Discord.

🔹 The Problem

  • Traditional: serverIndex = hash(key) % N
  • When N changes → most keys remap
  • Causes cache avalanche/miss storm

🔹 Consistent Hashing Ring

  • Hash servers and keys onto circular ring (0 to 2^n-1)
  • Keys map to first server found clockwise
  • Adding/removing server only affects neighbors
  • Average keys moved: K/N

🔹 Virtual Nodes (VNodes)

  • Each physical server → multiple virtual nodes
  • More virtual nodes = more even distribution
  • Typical: 100-200 virtual nodes per server
  • Trade-off: Memory vs. distribution evenness

📖 Chapter 6: Design A Key-Value Store

📋 SUMMARY
Design a distributed KV store like DynamoDB, Cassandra. Based on CAP theorem: must choose Consistency or Availability (Partition tolerance is required). Core: partitioning, replication, consistency, failure handling.

🔹 Basic

  • We can store everything in memory in a single server,but data is a issue
  • Data Compression can be used
  • Store frequently used data in memory rest on disk, but this also fails after some time.

🔹 CAP Theorem

  • C (Consistency): All nodes see same data
  • A (Availability): System responds to every request
  • P (Partition Tolerance): Works despite network failures
Must choose P (network failures inevitable). Then: CP (banking) or AP (social media)

🔹 Data Partitioning (Sharding)

  • Goal: Even data distribution + minimal data movement
  • Technique: Consistent Hashing
  • Servers placed on a hash ring
  • Key stored on first server clockwise
  • Virtual nodes: More nodes for higher capacity servers
  • Advantage: Easy scaling (add/remove servers with minimal rebalancing)

🔹 Data Replication

  • To achieve high availibility and reliability
  • N = Number of replicas
  • After key placement, walk clockwise
  • Select first N unique physical servers
  • Replication is asynchronous
  • Replicas placed across different data centers for reliability

🔹 Quorum Consensus (Consistency), to synchronije data across replicas

  • N = Number of replicas
  • W = Write quorum (ACKs needed)
  • R = Read quorum (responses needed)
ConfigBehavior
W + R > NStrong consistency guaranteed
W = 1Fast writes, risk of data loss
R = 1Fast reads, may read stale

Inconsistency Resolution (Versioning + Vector Clocks)

Why Needed?

  • Replication improves availability but replicas can diverge.
  • Concurrent updates on different replicas create conflicting versions.

Versioning

  • Every update creates a new immutable version.
  • System must detect:
    • Ancestor/Descendant → No conflict
    • Sibling Versions → Conflict

Vector Clock

Represents version history using: D[(Server, Version), ...]

Write Rules
  • If server entry exists → increment version.
  • Else → add (Server,1).

Example

  D1 = [(Sx,1)]
  D2 = [(Sx,2)]
  D3 = [(Sx,2),(Sy,1)]
  D4 = [(Sx,2),(Sz,1)]   ← concurrent update
  
  Conflict(D3,D4)
  
  Resolved:
  D5 = [(Sx,3),(Sy,1),(Sz,1)]

Conflict Detection

Ancestor (No Conflict) 
  A = [(S0,1),(S1,1)]
  B = [(S0,1),(S1,2)]
  
  A → B (ancestor)
Sibling (Conflict) 
  A = [(S0,1),(S1,2)]
  B = [(S0,2),(S1,1)]
  
  Conflict

Rules

  • X is ancestor of Y if every counter in Y ≥ corresponding counter in X.
  • Conflict exists when neither version dominates the other.

Pros

  • Detects concurrent writes.
  • Preserves causality/history.
  • Enables conflict reconciliation.

Cons

  • Client may need conflict resolution logic.
  • Vector clock size grows with participating servers.
  • Pruning old entries reduces reconciliation accuracy.
Interview One-Liner:
Vector clocks track version history as (server, counter) pairs, allowing distributed systems to determine whether versions are descendants (safe overwrite) or concurrent siblings (conflict requiring reconciliation).

🔹 Failure Handling

  • Gossip Protocol (for failure detection): Nodes periodically share membership info
  • Sloppy Quorum + Hinted Handoff: Temporary failures
  • Merkle Trees: Detect & sync inconsistent data

🔹 Failure Detection (Gossip Protocol)

  • No single node declares failure
  • Each node keeps membership list + heartbeat counter
  • Heartbeats shared with random nodes periodically
  • No heartbeat for threshold time → mark node down

🔹 Handling Temporary Failures

  • Sloppy Quorum: Use first W/R healthy nodes, instead of enforcing
  • Hinted Handoff: Healthy node stores data temporarily
  • When failed node recovers → data handed back

🔹 Handling Permanent Failures

  • Anti-Entropy: Sync replicas periodically
  • Merkle Trees: Hash tree for efficient diff detection
  • Compare root → traverse only mismatched branches
  • Sync only inconsistent buckets (not full data)

🔹 Data Center Outage

  • Replicate across multiple data centers
  • System remains available if one DC fails

🔹 Final Architecture

  • APIs: get(key), put(key,value)
  • Coordinator: Routes client requests
  • Consistent hashing ring
  • Fully decentralized (no single point of failure)
  • Replication across nodes

🔹 Write & Read Path

Write: Commit log(write request is persisted on a commit log file) → Memory Cache → SSTable (when full memory cache is full)

Read: MemCache → Bloom filter(used to figure out which SSTables might contain the key) → SSTables

🔹 API Endpoints

  • URL shortening

      • POST api/v1/data/shorten

    • request parameter: {longUrl: longURLString}
    • return shortURL
  • URL redirecting

      • GET api/v1/shortUrl

    • Return longURL for HTTP redirection

🔹 Redirect Types

301 Permanent302 Temporary
Browser cachesEvery request hits server
Reduces server loadBetter for analytics

🔹 Two Approaches

Hash + CollisionBase62 (Recommended)
Hash URL, take first N charsGenerate unique ID → Base62
Handle collisions with DB,by appending a string until unique 1st N charsNo collisions

🚀 High-Level Architecture

  • 👤 User sends request → short URL
  • ⚖️ Load Balancer distributes traffic
  • 🖥 Web Servers handle application logic
  • ⚡ Cache (Redis) checked first (fast lookup)
  • 🗄 Database fallback on cache miss

📖 Chapter 9: Design A Web Crawler

📋 SUMMARY
Design Googlebot. Crawls web to discover/index content. Key challenges: Politeness (don't overwhelm servers), Deduplication, Scale (billions of pages). Trade-offs: Freshness vs. Politeness, BFS preferred over DFS.

🔹 Workflow

Seed URLs → URL Frontier → Fetch → Parse → Dedup → Store → Extract URLs → Repeat

🔹 Non-functional requirements

  • Scalability: billions of pages to read
  • Robustness: The web is full of traps. Bad HTML, unresponsive servers, crashes, malicious links, etc.
  • Politeness: Not too many requests within short period of time
  • Extensibility: Min changes to support new content types

🔹 Core Components

  • DFS vs BFS: BFS is used
  • URL Frontier: Priority queues + per-host queues for politeness
    • Politeness:
    • Mapping table for Queue to host mapping

      • 🔹 Politeness

      • Cache and respect robots.txt
      • Maintain per-host delay (1 request/sec)
      • Use separate queues per host

    • Priority:

      • Front queues: manage prioritization
      • Back queues: manage politeness
    • Storage for URL Frontier:

      The majority of URLs are stored on disk, so the storage space is not a problem. To reduce the cost of reading from the disk and writing to the disk, we maintain buffers in memory for enqueue/dequeue operations. Data in the buffer is periodically written to the disk.

  • Url filter
  • Freshness: Must recrwal to update pages, recrawl on page update history and recrwal imp pages 1st and more frequently
  • HTML Downloader: Respects robots.txt
  • Performance Optimizations: Distributed crawl, Cache DNS Resolver, Locality(crawler closer to website host), Short timeout(for late or no responses)
  • Robustness: Consistent hashing(to distribute load), Save crawl states and data(to guard against failures), Exception handling, Data validation
  • Extensibility
  • Detect and avoid problematic content: Redundant content(hashes or checksums), Spider traps(keep a max length of url), Data noise(adds,spam etc.)
  • Content Dedup: SimHash/MinHash for similarity
  • URL Dedup: Bloom Filter (space-efficient)
  • Url seen? Bloom filter and hash table

📖 Chapter 13: Design A Search Autocomplete System

📋 SUMMARY
Design Google's typeahead. Must return suggestions within 100ms. Key data structure: Trie (prefix tree). Trade-off: Freshness vs. Performance (can't update trie in real-time at scale).

🔹 Trie with Top K Caching

Bcoj querying an rdms is inefficient

  • Each node stores: character, children, top K suggestions
  • Pre-compute top K for each prefix → O(1) lookup
  • Trade-off: More storage, much faster reads

🔹 System Components

  • Data Gathering: Query logs → MapReduce → Weekly batch

      Trie DB

    • Document store: Since a new trie is built weekly, we can periodically take a snapshot of it, serialize it, and store the serialized data in the database. Document stores like MongoDB [4] are good fits for serialized data.
    • Key-value store: A trie can be represented in a hash table form [4] by applying the following logic: • Every prefix in the trie is mapped to a key in a hash table. • Data on each trie node is mapped to a value in a hash table.
  • Query Service: Cache first → Trie lookup

    In case the data is not in Trie Cache, we replenish data back to the cache. This way, all subsequent requests for the same prefix are returned from the cache. A cache miss can happen when a cache server is out of memory or offline.

      Query service optimijations

    • AJAX request(sends req without refreshing page)
    • Browser caching(cache results in browser)
    • Data sampling(log only 1 out of N queries in logs for large scale)
  • Filter Layer: Remove inappropriate suggestions

🔹 Scaling

  • Shard by prefix, shard manager splits based on historical query pattern smartly

  • CDN caching for top prefixes
  • ~1GB trie fits in memory

🎬 Video Transcoding Architecture (Cloud-Based)

🔹 Preprocessor:

• Generates DAG from config

DAG Example: Download → Transcode

🔹 DAG Scheduler:
• Breaks DAG into stages and tasks
• Pushes tasks to resource manager queue
• Enables parallel execution

Stages:
Stage 1 → Video / Audio / Metadata
Stage 2 → Encoding, Thumbnail, Audio Encoding

🔹 Resource Manager:
• Manages task execution efficiently
• Uses queues + scheduler

• Task Queue → pending tasks (priority)
• Worker Queue → available workers
• Running Queue → active tasks
• Scheduler → assigns best worker to task

🔹 Error Handling & Fault Tolerance

Types of Errors:
• Recoverable → Retry (e.g., transcoding failure)
• Non-recoverable → Stop + return error (e.g., invalid format)

🔄 Retry Strategy:
Retry few times → if still failing → return error

🧩 Component-wise Handling:
Upload → Retry
Split Video → Fallback to server-side split
Transcoding → Retry
Preprocessor → Regenerate DAG
DAG Scheduler → Reschedule task
Resource Manager → Use replica queue
Task Worker → Retry on new worker
API Servers → Stateless → route to another instance
Cache → Replication → use other nodes
DB Master Down → Promote slave
DB Slave Down → Use another slave + replace node

🎯 Key Idea:
Retry + Redundancy + Failover = High availability

🔹 Failure Handling & Resilience

🎯 Goal:
Ensure system availability using redundancy, failover, and recovery

⚙️ Infrastructure Failures:
Load Balancer → Heartbeat → failover to secondary
Block Server → Other servers pick unfinished jobs
Cloud Storage → Multi-region replication (fetch from other region)

🖥️ Service Failures:
API Servers → Stateless → redirect traffic via LB
Notification Service → Clients reconnect on failure (gradual recovery)

🧠 Cache & Queue:
Cache → Replicated → use other nodes + replace failed one
Queue → Replicated → switch to backup queue

🗄️ Database Failures:
Master Down → Promote slave → create new slave
Slave Down → Use other slaves → replace node

🎯 Key Strategy:
Replication + Failover + Retry = High availability
